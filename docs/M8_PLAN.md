## 033-1c result (2026-11-03): per-tick cost model
Tool: `tools/tick_cost_record.py` (cycles and routine-entry counts of every tick of scenarios A, B, C, D on the oracle; 33,800 usable ticks) and a least-squares fit in Python against the draw-call logs (`scratch/tick_calls_X.txt`, 5,231 ticks with both).
* **Model (in `port/src/core/gamedriver.h`, `tickCostCycles`):** cost of an ordinary tick = 3,033 + per drawing call of type 1..6 {1,458; 1,789; 2,026; 3,745; 377; 864} cycles; other types 0.
* **Quality (V, measured):** R2 0.970; residual 566 cycles per tick (the flat 4,870 had 3,279). Fitting on three scenarios and testing on the fourth: total time within **0.1-0.6 %** of the oracle (A 1.0012, B 1.0015, C 1.0041, D 0.9945), while the flat figure was off by -3.8 % to +4.5 % per scenario (-1 % to -8 % in the earlier all-ticks comparison). With a model of all routine entries the fit reaches R2 0.98 (total within 0.2 %), but the port cannot count those routines.
* **Not exact:** it is an approximation (I); single ticks can be off by up to ~16,000 cycles (max residual), the totals are close. Types 7-12 were not in the fit. Only levels/situations in A-D (level 1, one death, one level end). Higher levels are not checked (needs recordings with cycles; the E/L recordings have none).
* The live game (`pacman_play`) now charges `drv.tickCycles()` per tick instead of the flat 4,870. Tests: 123 C++ tests, 0 failed (a new unit test for the arithmetic); a 8 s live run exited cleanly. I did not watch it.
