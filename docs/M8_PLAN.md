## 033-1 result (2026-11-03): pacing audit, findings only (no code changed)

* Ordinary ticks (2,990) cost **4,843 cycles on average, but between 2,987 and 19,518** (standard deviation 2,779). ## 033-1c result (2026-11-03): per-tick cost model
Tool: `tools/tick_cost_record.py` (cycles and routine-entry counts of every tick of scenarios A, B, C, D on the oracle; 33,800 usable ticks) and a least-squares fit in Python against the draw-call logs (`scratch/tick_calls_X.txt`, 5,231 ticks with both).
* **Model (in `port/src/core/gamedriver.h`, `tickCostCycles`):** cost of an ordinary tick = 3,033 + per drawing call of type 1..6 {1,458; 1,789; 2,026; 3,745; 377; 864} cycles; other types 0.
* **Quality (V, measured):** R2 0.970; residual 566 cycles per tick (the flat 4,870 had 3,279). Fitting on three scenarios and testing on the fourth: total time within **0.1-0.6 %** of the oracle (A 1.0012, B 1.0015, C 1.0041, D 0.9945), while the flat figure was off by -3.8 % to +4.5 % per scenario (-1 % to -8 % in the earlier all-ticks comparison). With a model of all routine entries the fit reaches R2 0.98 (total within 0.2 %), but the port cannot count those routines.
* **Not exact:** it is an approximation (I); single ticks can be off by up to ~16,000 cycles (max residual), the totals are close. Types 7-12 were not in the fit. Only levels/situations in A-D (level 1, one death, one level end). Higher levels are not checked (needs recordings with cycles; the E/L recordings have none).
* The live game (`pacman_play`) now charges `drv.tickCycles()` per tick instead of the flat 4,870. Tests: 123 C++ tests, 0 failed (a new unit test for the arithmetic); a 8 s live run exited cleanly. I did not watch it.

## 033-3b result (2026-11-03): the timing of the death sequence and GAME OVER, measured on 245 deaths
Tools: `tools/death_timing.py` (forced and random deaths with cycle-stamped drawing events, zero page and dot map; modes multi / forced / forced2 (other levels and lives) / gameover), `tools/death_lib.py`, `tools/death_model_analyse.py`, `tools/export_deaths.py` (scratch/death_timing.bin for the C++ test, flag `--deaths`, now in tools/full_suite.sh).
* **What the sequence depends on (V, 245 deaths):** everything before the rebuild is fixed except two things: Pac-Man's **shift x mod 7** (each shifted frame draw costs 0 to 4,062 cycles more) and a small **page-crossing extra of 0 or 56 (up to 66) cycles per frame** that depends on the screen contents/place (not modelled; the middle value 28 is used). The stillness (761,750 and 777,378), the erase steps, the six frames, their sounds (1,522 after each frame) and the 316,902 before the rebuild are constants. The **rebuild** costs 42,998 + 214 per small dot + 851 per energizer + 972 per score digit (score and high score) + 1,588 per life (fit on 220 deaths, residual sd 30). READY wait 3,114,542 as in 033-2.
* **Model in C++:** `port/src/core/deathtiming.{h,cpp}` (`deathTimeline`). **Check against the recordings (tests/test_deathtiming.cpp, 220 deaths with the dot map): the first erases, image and so on are exact; the largest error is 56 cycles at the first frame, growing by about 28 per frame to 196 at the last frame, 282 at the last sound, 224 at the rebuild; at the next tick the mean absolute error is 200 cycles (0.2 ms) and the mean signed error 4 cycles; ONE of the 220 deaths has a rebuild 1,700 cycles longer than the model (cause not found).** So the model is not cycle-exact: errors stay under 0.3 ms, apart from the one outlier (1.6 ms).
* **The catching tick itself** costs 6,273 to 18,916 cycles up to its last drawing (mean 8,917); the port charges the mean (`kCatchTickCycles`), so each death's total is off by up to about 10,000 cycles (10 ms) from that alone. Not modelled further.
* **GAME OVER (5 runs, identical): the same animation, the letters start 18,585 cycles after the last frame is erased, drawn in 2,052; then the original waits exactly 10,453,613 cycles (10.22 s) before the next screen (the attract/title screens, first drawing at that point).** The port now plays the animation, the words and this wait, then (placeholder, until the title/attract flow exists, 033-4/033-5) starts a new game at once.
* In `pacman_play` the death animation plays with the six sounds scheduled at their frames; GAME OVER is a sequence too. Tests: 126 C++ tests, 0 failed (full suite arguments incl. --deaths). A 12 s live run exited cleanly; the death and GAME OVER paths were exercised by a forced catch in a unit test (22 resp. 21 steps, ascending times, 6 sounds), not watched.
