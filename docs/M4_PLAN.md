# M4 plan: the game core, split into small checkable pieces (TASK-029, 2026-11-02)

Decision already made (D2 = A, 2026-10-29): **oracle-driven reconstruction**. The C++ code is written by me from the analysis documents, in readable form, and every piece is checked against the original program running on our headless 6502 machine (the "oracle"). Nothing is translated mechanically.

## 1. The unit of work: the tick
The golden traces (docs/GOLDEN_TRACES.md) already define it: **one tick = one pass of the game's main loop** (counted at `$7861` with `$E8 = 0`). The port needs no cycle timing for the game *logic*; inputs are keyed by tick; the cycle clock (TASK-028l) only decides how fast ticks happen in real time. (Open, to settle in 029h: the original's cost per tick varies from 2,987 to 27,950 cycles, so a faithful *speed* needs each tick's cycle cost too; the analysis so far says the cost comes from what is drawn, so the drawing code will have to report an approximate cost. Until then ticks may be run at the mean, about 7,100 cycles, and this is a known deviation, to be written into KNOWN_ISSUES when 029h is done.)

State = the "logical state" of the golden traces: zero page `$52-$6F`, `$78 $79 $E8 $E9`, the four ghost records `$84-$D3`, the maze map (896 bytes), plus what the pieces below add (per-piece lists). The C++ state is a plain struct with readable names, plus functions `toOracleLayout()` / `fromOracleLayout()` so that the test can hash it exactly like the oracle (the same chain hash as the golden traces).

## 2. How each piece is tested (hybrid testing, because the ghosts come later in M5)
A new local tool records, **per tick**, the complete logical state and the inputs of the golden scenarios A-D (and extra scenarios when a piece needs them) into `scratch/` (git-ignored; original-derived). A piece is tested by running only the C++ code of that piece for each tick on the oracle's state at the start of the tick, and comparing only the *fields that piece is responsible for* with the oracle's state at the start of the next tick. Everything the piece does not own is copied from the oracle ("fed"). Pieces are joined at the end (029h), when the fed fields shrink to the ghost fields only, and M5 removes those.

## TASK-029a done (2026-11-02): the per-tick recorder and reader
* **Tool:** `tools/record_ticks.py A|B|C|D` replays a golden scenario with its stored inputs and pokes and writes **the logical state of every tick** to `scratch/ticks_X.bin` (local, git-ignored, derived from original data). It refuses to write unless the replay reproduces the golden file's checkpoints, samples, events, tick count and final hash, and unless the chain hash over the recorded states equals the golden final hash. Format and state layout: in the tool's header and in `port/src/core/ticktrace.h` (state = 1,010 bytes: `$52-$6F`, `$78 $79 $E8 $E9`, `$84-$D3`, the 896-byte map).
* **Recorded (V, all four reproduce the golden final hash):** A 8,090 ticks (1,207 key presses, 0 pokes); B 4,610 (1,225; 1); C 6,195 (1,380; 2); D 14,937 (1,636; 47). Total about 34 MB. Start state of A: lives `$58 = $83`, level 1, 248 items left.
* **Key codes in the files:** the Apple II code as the game receives it (7-bit ASCII with bit 7 set: A = `$C1`, Z = `$DA`, left `$88`, right `$95`); the same codes `GameWindow::popKey` produces. My first version failed to write the inputs because the golden file stores some keys as letters and some as numbers; fixed by converting (no data was lost: the files are written only at the end).
* **C++ reader:** `port/src/core/ticktrace.{h,cpp}` (`TickTrace::load`, `state(t)`, `at(t, address)`, `inputs()`, `pokes()`, `chainHash()`, `stateOffsetOf`). Tests: `port/tests/test_ticktrace.cpp`: a synthetic file (offsets, parsing, chain hash against an independent computation in the test, refusal of a damaged tail, a cut file, a wrong magic and a missing file) always runs; with `--ticks a.bin,b.bin,c.bin,d.bin` the C++ chain hash over all recorded states equals the golden hash for each of the four (V), and a file with one flipped bit is rejected (shown by running it). C++ suite: 62 tests, 0 failed; CMake route builds and ctest passes 2 of 2.
* **Limits:** the recording gives states at tick starts only; per-tick draw calls and the cycle cost of each tick are not in it (029g/029h need them: a separate recorder will be added there); the zero page changes in almost every tick (8,089 of 8,089 in A), so most of it is timers and counters, not events.

## TASK-029d split and TASK-029d1 done (2026-11-02): Pac-Man's step timer
* **Why split:** reading `$78A5-$7B2F` shows that "Pac-Man's movement" is one tangled routine: junction arrival and direction acceptance (`$78A5-$7961`, fields `$62 $63 $64 $65` and the tunnel flags `$69 $6A $6C`), the step itself with the sprite animation counters (`$7968-$79A1`, `$66 $1F`, fields `$60 $61`), a special case at (`$8A..$8D`, `$6B`) with `$E7` (`$79CD-$79FD`), the cell counters `$6A $6B $6C $6D` and the dot test (`$7A01-$7A6A`, cell address = `$623A + 32 * $6A + $6B`), and the eating code (`$7AAC-$7B2F`). That is d2 (junctions and direction), d3 (the step and the cell counters), d4 (eating; this is also piece 029e's start) rather than one piece. The timer, which comes first in the tick, was done now as d1.
* **d1 code:** `port/src/core/steptimer.{h,cpp}` (`StepTimer`, `StepTables`, `loadStepTables`). Every tick `$59 -= 1`; at zero it is reloaded with `$7851[min(level,15)]`, +1 for each frightened flag of ghosts 2 and 4 (`$A0`, `$C8`), -1 for each eyes flag of ghosts 1 and 3 (`$8D`, `$B5`), +1 while the dot-penalty counter `$F3` (not in the logical state; kept by the StepTimer) is non-zero; eating an item adds `$7A8C[min(level,15)]` at once and sets `$F3 := $7A9C[...]` (code read at `$7AAC-$7ABB`). The three tables come from the data pack (they lie inside manifest ranges `$7843+30` and `$7A8C+32`).
* **Tests (V):** `port/tests/test_steptimer.cpp`: three synthetic tests (countdown and reload, ghost-state terms incl. the ones that must not count, eating with the `$F3` aftermath, levels above 15) and the oracle comparison: on all four recordings the C++ timer, fed with the oracle's state at each tick and told when an item was eaten, predicts `$59` of the next tick in **all 33,757 compared ticks** (3,660 reloads, 228 items eaten, `$F3` effects included); 71 ticks where a life or level start sets the timer by another routine are skipped and counted. A first run failed in 6 ticks (scenarios B and C) because MY test did not count the last item of a level as eaten (the item counter jumps to 248 and the level rises); the code was right, the test was wrong, and the level 2 reload of 9 = 8 + 1 (`$F3`) confirms the rule. A deliberate mutation (ghost 4 adds 2) made the tests fail; reverted. C++ suite: 77 tests, 0 failed.
* **Limits:** only levels 1-3 occur in the recordings, so entries 4-15 of the three tables are taken from the pack but never exercised; the extra rule "from level 5 on" mentioned in PACMAN_RULES.md (an extra +1 under a bit condition) is not in this code and was not seen (levels < 5): U; the 71 skipped restart ticks belong to the start-of-life piece.
* **Observed once, not explained:** the first `ctest -C Release` run after the CMake rebuild reported the unit test as failed; four reruns (and the output of the failing case was not captured) all passed. The window tests (they open real windows and wait for timers) are the most likely cause, but that is a guess (U). If it happens again, run with `--output-on-failure` at once.

## TASK-029d1b done (2026-11-02): the step timer at higher levels (closing the limits of 029d1)
* **Why:** the golden recordings reach level 3 only, so table entries 4-15 and the "extra rule from level 5 on" were untested. **New recorder** `tools/record_levels.py L...` plays a game, POKES the level counter `$55` to L at tick 5 (the tables are read live from `$55`), plays 700 ticks with random keys and tops up the lives; files `scratch/ticks_L04.bin ... L21.bin` (14 levels: 4-16 and 21; local, git-ignored; chain hash of the recording in the header, level 4/8/12/15 recorded twice with identical hashes, the others once). This is an experiment scenario, not a natural level sequence; it tests code that reads `$55` live (the tables), not level-start set-up.
* **Result (V):** levels 4-14: the existing StepTimer matched at once (0 mismatches). Levels 15, 16 and 21 mismatched (25, 14 and 22 ticks): Pac-Man was delayed 1 tick more than the tables say when eating. **Cause found by tracing writes of `$59` on the oracle: a carry quirk.** The eating code is `CLC; JSR $6D1E; TAX; LDA $7A8C,X; ADC $59` and `$6D1E` ends with `CMP #$0F`, which leaves the carry SET for every level >= 15, so `ADC` adds 1 more (table entry 0 + carry 1). Rebuilt in `StepTimer::itemEaten` (`level >= 15` adds 1), with a synthetic test (level 14 no delay, 15 and 30 delay 1). After the fix **all 18 recordings (A-D and the 14 level files) match: 43,531 compared ticks, 5,559 reloads, 460 items eaten, 0 mismatches.**
* **The "extra rule from level 5 on" (PACMAN_RULES.md) is now understood from the code (`$8B34-$8B65`, I; not yet seen on the oracle):** it is in the ghost/Pac-Man contact test, not in the step timer. When level >= 5, a ghost is on the same row or column as Pac-Man and closer than 10 units, then: a ghost moving horizontally (direction bit 1 of `$72`) looks at Pac-Man's Y (X if Y is 0), otherwise at Pac-Man's X, and if bit 1 of that coordinate is clear Pac-Man's `$59` is increased by 1. Implemented as `StepTimer::nearGhostDelays` / `applyNearGhostDelay` and used in the test only as an explanation of otherwise unexplained +1 ticks. **It never fired in the 14 level recordings (0 explained), so it is NOT verified; the function is untested against the oracle.** Its timing belongs to the ghost steps (M5/029f). To see it, a run is needed where a ghost passes close to Pac-Man at level >= 5 (e.g. several seeds with Pac-Man put next to a ghost): left as an open item.
* **Honest limits that remain:** the level pokes only cover 700 ticks per level and few eaten items (9-24 per level); F3 effects at class 15 are not distinguishable (their start values are 0); levels 17-20 and >21 share class 15 by the code (`CMP #$0F`) and only 15, 16 and 21 were run.
* Not re-run this turn: the CMake build (no new source files were added; only edits in existing files).
