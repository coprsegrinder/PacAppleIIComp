# Data pack (TASK-026, milestone M1; decision D1-A)

Code: `port/src/datapack/` (builder, loader, generated manifest), `port/src/app/pack_main.cpp` (`pacman_pack`), tests in `port/tests/test_datapack.cpp` and `test_real_image.cpp`. Manifest generator: `tools/make_manifest.py`.

## What the pack is
A single local file (suggested name `pacman.pmpk`, git-ignored via `*.pmpk`) holding the **data bytes of the game program** (the parts that analysis classed as *not code*), copied from the player's own disk image. The C++ game never contains these bytes in its source; it reads them from the pack. The pack is **never committed or distributed**.
Only data is stored: no code bytes, no DOS tracks, no disk image. The reconstructed game code is written by us (decision D2-A).

## Manifest (what goes in)
60 address ranges of the relocated program ($4000-$A9FF), **16,680 bytes** = every run that is not in the code map (docs/CODE_COVERAGE.md; 10,456 code bytes are excluded). Generated by `tools/make_manifest.py`; the committed `manifest.cpp` holds addresses and lengths only, and `--check` confirms it matches a fresh analysis (done 2026-10-29: matches). This is deliberately mechanical, not subjective: whatever analysis calls data goes in, and the manifest is regenerated as analysis improves.
Caveats (U): the 146 "unclassified" bytes and the gaps may still contain code that never ran in our scenarios; they are in the pack because they are not proven code. When analysis moves a range, the manifest version changes and old packs are refused (rebuild).

## File format (version 1, little endian)
| Offset | Size | Content |
|---|---|---|
| 0 | 8 | magic `PMPACK01` |
| 8 | 4 | format version = 1 |
| 12 | 4 | manifest version = 1 |
| 16 | 32 | SHA-256 of the **program body** the pack was built from |
| 48 | 4 | blob count N (at most 4096) |
| 52 | N x 44 | table: u32 address, u32 length, u32 file offset, 32-byte SHA-256 of the blob |
| ... | | blob bytes, in table order |
| end-32 | 32 | SHA-256 of everything before it |
Size for the real game: 52 + 60 x 44 + 16,680 + 32 = **19,404 bytes**.

## Builder rules (`buildPack`, `pacman_pack build <image> <pack>`)
1. The image must be accepted by the verifier (exact image, or same game program). Otherwise: refused, nothing written.
2. The manifest must be ascending, non-overlapping, non-empty ranges inside the program.
3. The file is written to `<pack>.tmp` and renamed: a failed build never leaves a half-written pack; the disk image is only read.
4. Because only program data is stored, a disk with other DOS tracks gives a **byte-identical pack** (tested).

## Loader rules (`loadPack`, `pacman_pack info <pack>`)
Refuses unless all hold: signature, format and manifest versions; whole-file hash; stored program hash equals the expected program body hash; table sane (count, non-zero lengths, addresses inside $4000-$FFFF, ascending, no overlap, offsets inside the data area); **every blob's hash**. `find(address, length)` returns a view only if one blob covers the whole range.
Tested: every single-byte change and every truncation/extension of a pack is refused (exhaustive on a synthetic pack), tables that are inconsistent but carry valid hashes are refused, a pack for another program is refused.

## What this does and does not give (honest limits)
* **Integrity, not secrecy or anti-tamper:** the hashes catch accidental damage and wrong-game packs; anyone can recompute them. The pack is a local cache of the user's own data, not a protection scheme.
* Not compressed or encrypted. Blobs are unnamed (address only); names come with later milestones.
* The loader does not check that the original disk still exists (by design: after the pack exists the game does not read the disk, rule 4 as interpreted in D1-A).
* Where the launcher stores the pack (proposal: `%LOCALAPPDATA%\PacmanApplePort\pacman.pmpk`) and the first-run dialogs belong to milestone M3.

## Verification done (V, 2026-10-29)
27 C++ tests pass (13 new for the pack, 1 new real-image test), both build routes. Real image: 60 blobs, 16,680 bytes, SHA-256 of the concatenated blobs `4754D38A...84F46`, equal to the value computed independently by the Python tool; a boot-track-altered disk gives the identical pack; a program-byte-altered disk gives no pack; the System Master gives no pack and no file; a damaged pack is refused by the CLI.
