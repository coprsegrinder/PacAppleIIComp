# Modernization phase (started 2026-11-04)

Spec given by the user (12 sections, in this order, each implemented, tested, documented and approved before the next): 1 Fullscreen, 2 Windowed mode improvements, 3 Pause menu, 4 Display mode, 5 Resolution, 6 Window borders, 7 Background (Black / Ambient Glow / CRT Bezel / Apple II Desktop), 8 Colour mode (Original / Native B&W), 9 CRT filter, 10 HDR, 11 FPS, 12 VSync.
Highest priority: the original gameplay (logic, timing, collisions, input, animations) must not change. External assets, shaders and filters: research and present them (source, licence, redistribution), and ask before downloading or integrating anything. Do not change the original simulation without explaining why and getting approval.

## Decisions by the user (2026-11-04)
1. **Viewport:** keeps the picture's own ratio, 280:192 = 1.458:1 (not 4:3). It is never stretched; black bars take the rest, horizontally and vertically, for 4:3, 16:9, 16:10, 21:9 and 32:9. Scaling is nearest neighbour. (My reading, to be corrected if wrong: the viewport is the largest WHOLE-NUMBER multiple of 280x192 that fits, so every Apple pixel is an exact block; below 1x it is shrunk by the largest fraction that fits.)
2. **Esc:** the original Esc behaviour (pause until any key) is replaced by the pause menu (Section 3).
3. **Renderer:** Direct3D 11 first ("Section 0"), because CRT filters, HDR, VSync and frame pacing need it.

## Audit of the existing program (before Section 0)
* Rendering: GDI `StretchDIBits` at a whole-number scale, repaint from a coarse window timer. Window: fixed client size 280x192 x scale; F11/Alt+Enter borderless full screen; Ctrl+Plus/Minus scale; F9 mute.
* Timing: the worker thread runs the game from the virtual 1,022,727 Hz cycle clock; the window thread only shows the newest page under a lock. So window changes cannot change game speed. One game tick is about 2,927 cycles = about 349 ticks per second, much faster than any display refresh (matters for Section 11).
* Input: window thread turns key events into Apple II key codes in a queue. Settings: none are saved yet. Menus: only the game's own text screens. Audio: WASAPI mixer. Build: build.bat (cl) + CMakeLists.txt, no third-party libraries.

## Section 0 - Direct3D 11 renderer (done 2026-11-04, TASK-034-0)
* `port/src/app/d3drenderer.{h,cpp}`: device (hardware, WARP software device as the second try), flip-model swap chain (DXGI Alt+Enter handling switched off, the window's own hotkey stays), the 280x192 picture as a dynamic BGRA texture, one fullscreen triangle drawn into the viewport with a point sampler, UNORM (no colour conversion), black clear. Shaders are compiled at start-up with the system `d3dcompiler`. No download, no new dependency (system libs d3d11, dxgi, d3dcompiler).
* `port/src/app/display_layout.h`: `computeViewport(clientW, clientH)`: pure function, whole-number scale, centred, fractional fit below 1x. Used by Direct3D and testable alone.
* `GameWindow`: uses Direct3D when it starts, otherwise (or with environment variable `PACMAN_GDI=1`) the old GDI drawing, which stays as the fallback. `WM_SIZE` resizes the swap chain. `captureFrame()` (tests) reads the back buffer.
* Present uses sync interval 0 for now (no waiting for the monitor); VSync is Section 12. Repaint is still driven by the window timer; frame pacing is Section 11.
* **Tests (V, tests/test_gamewindow.cpp):** layout for 11 screen shapes incl. 21:9, 32:9, 4:3, 16:10, exact fit, sub-1x; the Direct3D picture of a page with every byte different equals the CPU-scaled picture **byte for byte** (0 of 483,840 pixels differ at 3x; 0 differ at five other client shapes with bars on every side; 0 differ in full screen at 2560x1440, three round trips of Alt+Enter); the GDI fallback still draws. Suite 153/0. Live check: the real game's boot menu is drawn through Direct3D.
* Limits: the layout is whole-number scale only (a "fill" mode is not offered); an HDR or wide-colour swap chain is Section 10.

## Fix 2026-11-04: full screen showed a black screen with a white block (user report; broken since TASK-028k)
* **Cause (V, reproduced on a visible window with the window-only screenshot script, and by a failing test):** `GameWindow::setFullscreen` replaced the window style with `WS_POPUP` and so dropped `WS_VISIBLE`; Windows then treated the window as hidden and stopped drawing it. The old fullscreen test used hidden windows (`visible = false`), where the flag is irrelevant, so it never saw this.
* **Fix:** the popup style keeps the saved window's `WS_VISIBLE`. New test `visible_window_full_screen_stays_visible_and_shows_the_picture` (a visible window: stays visible, covers the monitor, Direct3D picture byte-equal, F11 back restores the 840x576 client). Suite 154/0. Real game checked: full screen fills the monitor with the picture centred at the largest whole-number scale, F11 returns to the window.
* Lesson recorded: window behaviour must also be tested on VISIBLE windows.

## Decision 4 (2026-11-04, for Section 4): Fullscreen vs Borderless Fullscreen
User: "Go with your recommendation." So: **Fullscreen = true exclusive fullscreen** that switches the display to the chosen Resolution (Section 5), with a safe fallback when the mode is unsupported; **Borderless Fullscreen = the current borderless window at the desktop's native resolution, and the default**; the settings page notes that Borderless gives the sharpest picture because exclusive mode's scaling is done by the monitor/GPU. Reasons: on Windows 10/11 a flip-model borderless window has the same latency as exclusive, alt-tab and overlays are better, and VRR/HDR work from borderless; exclusive only adds a real resolution change, a forced refresh rate and old-hardware compatibility.

## Section 3 - Pause menu (done 2026-11-04, TASK-034-3)
* **Esc opens the menu, anywhere** (boot menus, attract loop, prompts, the game, GAME OVER). The original Esc pause (wait for any key) is replaced, as decided; the key never reaches the game. While the menu is open NO key reaches the game; the other port hotkeys (F11, Alt+Enter, F8, F9, Ctrl+/-) still work. Esc held down opens it once.
* **Entries, in the specified order:** Resume - Graphics Settings - Quit Game. Esc on the main page = Resume; Esc on a sub-page = back. Keyboard: Up/Down (wraps), Enter or Space = choose, Esc = back. Mouse: moving over an entry selects it, left click chooses it, the wheel moves the selection; the mouse works at any window size (position mapped through the viewport). A click beside the entries does nothing.
* **Graphics Settings page** holds what exists now: "Window Borders: On/Off" (the Section 2 feature) and Back. The settings of Sections 4 to 12 will be added to this page as they are built (display mode, resolution, background, colour mode, CRT filter, HDR, FPS, VSync); there are no dummy entries.
* **Quit Game asks first:** "QUIT GAME? - CONFIRM / CANCEL", with CANCEL selected (Enter twice never quits), Esc cancels back to the menu, Confirm closes the window the normal way (game threads end, audio, Direct3D and the window are released in order). No settings or save files exist yet that could be corrupted; when Section 4 adds the settings file it will be written to a temporary file and renamed. Works in full screen, windowed and bare-window modes (the same close path).
* **Look:** drawn on the picture itself in the Apple II character ROM font: the game dimmed to a quarter, a black panel with a white frame, the selected entry in inverse video. Scales with the picture, the same in every mode. (Needs the character ROM, which the release ships next to the program.)
* **A real pause (V):** `PauseGate` (pausegate.h) stands between the menu and both game loops (`runGame`, `runMenus`): while the menu is open the loop does nothing, the cycle clock is SUSPENDED (no time is earned and none is made up afterwards, so no fast-forward on resume), the audio mixer is paused (silence; nothing queued is consumed, the sounds keep their place and continue from the same sample). Tests: gate with a fake clock (5 s in the menu: 0 cycles; 200 ms of running time = exactly the 204,545 cycles it earns, nothing skipped); audio (a 1 s sound paused for 1 s is still playing after 1.5 s and ends about 1 s later); the REAL program (tools/test_pause_menu.ps1, muted, 6 repeats, all pass): the running game changes between two shots; with the menu open two shots 4 s apart are identical; after Esc the game runs again; Cancel keeps it running; Quit Game + Confirm exits with code 0.
* **Closed menu does not interfere (V):** with the menu closed the Direct3D picture is byte-equal to the game's, keys reach the game as before (test); open: every pixel outside the panel is the game at 1/4 brightness, the panel has the text.
* **Borderless window and full screen:** while the menu is open the picture no longer drags the borderless window (the menu gets the clicks); the mouse pointer is hidden over the picture in full screen until the menu opens.
* **Tests added (suite 171/0):** menu keyboard/mouse logic (2), drawing and selection highlight, PauseGate, window integration (Esc, keys swallowed, dimmed picture, closing, mouse through the viewport, quit), borderless/pointer behaviour, audio pause; the old "Esc reaches the game" key test was changed to the new rule.
* **Also added: `--mute`** (the same as F9 at the start) so that tests which run the real program make no sound; all tests are silent (the C++ suite renders and checks sounds as numbers and the audio test plays silence).
* A flake found and fixed on the way: the menu keys ignored Esc while Ctrl was held; Windows reports the user's real keyboard state to posted keys, so a scripted Esc was lost when the user was typing. Menu keys now ignore Ctrl (Alt+Esc stays Windows').
Limits: no sound is played for menu navigation; the menu is not drawn with a mouse-hover highlight beyond the selection band; the Graphics page cannot yet change anything but the borders (see above); gamepad navigation arrives with the gamepad option.

## Section 4 - Graphics Settings: Display Mode (done 2026-11-04, TASK-034-4)
**The three modes (decision 4):** *Fullscreen* = true exclusive full screen (the Direct3D swap chain takes over the monitor); *Borderless Fullscreen* = a borderless window over the monitor at the desktop's own resolution (the default); *Windowed*. Changed from the pause menu (Esc, Graphics Settings, "Display Mode": Enter / Right = next, Left = previous, or click it; order Fullscreen, Borderless Fullscreen, Windowed), by F11 / Alt+Enter (between Windowed and the full screen mode last used), or by `--display fullscreen|borderless|windowed` (written to the settings like a menu change). The menu stays open and keeps the game paused while the mode changes.
| Requirement | Result |
|---|---|
| Works reliably | V: Windowed -> Borderless -> (Fullscreen) -> Borderless -> Windowed and straight Windowed <-> Fullscreen, repeated; the window comes back exactly as it was (same picture area, same place); the Direct3D picture is byte-equal in every mode; 25 mode changes during 150,000 game ticks |
| Reflected correctly | V: `displayMode()` is the actual mode; the menu shows it; refused Fullscreen shows the notice "FULLSCREEN NOT AVAILABLE: BORDERLESS USED" and the menu/settings show Borderless |
| Borderless uses the native resolution | V: the picture area equals the monitor rectangle (2560x1440 here), no list resolution |
| No effect on the game or timing | V: game page/score/level identical with 25 mode changes while 150,000 ticks run; the cycle clock hands out exactly the cycles the time earned across 8 changes in 1 s (1,023,280 = 1,023,280, none skipped) |
| Saved and restored | V: settings file (below); real program: restart restores the mode and the window size; first run without a file starts Borderless; a damaged file starts with the defaults |
**Settings file** `%LOCALAPPDATA%\PacmanAppleIIPort\settings.ini` (`PACMAN_SETTINGS` or `--settings` name another): plain `key=value` lines (display_mode, fullscreen_kind, window_borders, window_x/y/w/h = the window as the user left it); unknown keys ignored, bad values = defaults; **written atomically** (temporary file, then renamed over the old one; a failure leaves the old file untouched; tested with an unwritable temp name, a folder in the way, a read-only file, a missing drive). It is written on every change of these settings and once more when the window closes. A saved window place that is no longer on any monitor is moved to the primary monitor; a size larger than the monitor is cut; one below the minimum is raised (tests). `--scale N` still sets the window size and overrides the saved size; `Play-Game.bat` no longer passes it, so your window size is remembered.
**Exclusive Fullscreen - what is and is not verified:** the code enters it with `SetFullscreenState` on the monitor the window is on at the desktop's current resolution and refresh rate (no display mode change; the Resolution setting of Section 5 adds that), leaves it first on every other change and on close, leaves it on Alt+Tab (and enters it again when the window is active again), asks for the keyboard focus when it is chosen, and retries once when the window becomes active if it was refused at start-up (the saved choice is not overwritten by a start-up refusal). **On this development machine Windows refuses it for the test windows: `SetFullscreenState` returns `0x887A0022` (DXGI_ERROR_NOT_CURRENTLY_AVAILABLE), which is what Windows says to a window that is not the foreground window; the programs started by my test tools are never foreground.** The refusal path is tested (the borderless window is used, with the notice, the result is false, nothing else changes); the success path (really owning the monitor, the picture in it, leaving it again) could not be exercised here and needs a try in a normally started program. The `--log <file>` option writes a line per mode change with `foreground=`, `exclusive=` and the refusal code, for reports.
Tests added (suite 183/0): 4 settings tests (tests/test_settings.cpp), 7 display-mode window tests, `tools/test_display_modes.ps1` (real program, 8 checks). Menu: graphics page now Display Mode / Window Borders / Back (wider panel, one row per entry so that the later sections fit), with Left/Right to change a setting. Alt is now read from the key message itself (a physically held Alt no longer disturbs the menu keys or the tests).
Limits: no exclusive-mode refresh-rate or resolution choice yet (Section 5); a mode change in exclusive Fullscreen blinks the monitor as Windows does it.

## Decision 5 (2026-11-04, user): no exclusive Fullscreen - two display modes only
The user tried Section 4 and found three entries behaving as two: Borderless Fullscreen (fine) and two "windowed" ones, the second keeping the windowed picture where it was last placed with black everywhere else. That second one was the exclusive "Fullscreen" mode (the swap chain entered exclusive full screen but its back buffer stayed at the windowed size, so the picture did not follow). The user's decision: **keep Windowed and Borderless Fullscreen only.** Decision 4 (exclusive Fullscreen) is withdrawn and the spec's third option ("Fullscreen") is dropped by the user's choice.
Done: all exclusive code removed (the renderer's `setExclusive`, the activate/deactivate handling, the focus request, the refusal notice and the `--log` refusal fields); `DisplayMode` has two values; the menu entry "Display Mode" switches between BORDERLESS FULLSCREEN and WINDOWED (Enter, Left, Right or a click); F11 / Alt+Enter do the same; a settings file written by the earlier build (`display_mode=fullscreen`, `fullscreen_kind=...`) is read as borderless / ignored (tested); `--display fullscreen` is accepted as borderless. Suite 182/0 (the exclusive-only tests are gone, the transition test now cycles Windowed <-> Borderless 4 times with byte-exact pictures and exact window restore); `tools/test_display_modes.ps1` 8/8 and `tools/test_pause_menu.ps1` 9/9 on the real program.
For Section 5 (Resolution): with no exclusive mode, a listed resolution can only mean the size of the windowed picture area (and the internal render size); Borderless keeps the desktop's resolution as the spec says. To be agreed when Section 5 starts.
